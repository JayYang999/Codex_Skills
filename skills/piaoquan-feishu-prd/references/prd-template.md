# 票圈 PRD 模板规则

本文件是 PRD 生成规则，不是可直接复制的 PRD 正文。生成 PRD 时，不得把本文件的标题、说明性小节或规则文字当作额外的 PRD 内容。

## 固定文档框架

PRD 正文必须且只能按以下顺序使用 9 个一级标题：

| 顺序 | 一级标题 |
|---:|---|
| 1 | `变更记录` |
| 2 | `一、背景` |
| 3 | `二、需求分析` |
| 4 | `三、产品方案` |
| 5 | `四、需求详情` |
| 6 | `五、数据交付结果` |
| 7 | `六、指标分析` |
| 8 | `七、问题记录` |
| 9 | `八、需求排期` |

不得增加、删除、合并、改名或调换上述标题。明确禁止生成 `产品验收` 标题或章节；验收内容归入“四、需求详情”。

PRD 正文精确包含上述 9 个一级标题。在聊天预览中，每个一级标题序列化为 Markdown `# 标题`；写入飞书 XML 时，每个一级标题序列化为 `<h1>标题</h1>`。PRD 的独立文档名称是正文之外的元数据，不占用一级标题。本 skill 只向现有飞书文档追加内容，因此不输出 `<title>`，也不修改目标文档标题。

## 各章写作规则

### 变更记录

使用五列表格，列名和顺序固定为：`时间`、`版本号`、`变更人`、`主要变更内容`、`变更原因`。

`时间`、`版本号`、`变更人` 是必需事实；哪一项缺失就只询问该项，每次只问一项，不使用默认值、虚构值或自拟值。`主要变更内容` 可根据用户已确认的 PRD 范围作简洁概括。`变更原因` 只写用户明确提供的事实；用户未提供时保留空单元格，不因此阻塞起草，也不得推断或编造。

### 一、背景

这是首批重点写作章节。用连贯叙事说清：目标用户、当前问题、已确认的现状事实或数据、为什么是现在、不解决的后果，以及可衡量的目标。不要把这些要素拆成零散标签或问答堆叠。

### 二、需求分析

这是可选内容，但一级标题始终保留。如果用户尚未说明是否需要该章，起草前先询问；如果用户已经明确需要或不需要，直接遵循其选择，不重复询问。如需要，先读取现有上下文；只有分析类型或证据来源仍不清楚时，才继续确认可支撑内容：数据分析、用户研究、竞品分析或其他，不得对已知信息重复提问。只写用户选定且有依据的内容。如用户确认不需要，保留“二、需求分析”一级标题，其下完全留空。

### 三、产品方案

这是首批重点写作章节，也是面向老板对齐产品方向的方案概览。先说整体解决方案，再交代核心链路、本期范围和明确边界。方案必须能回应背景中的问题和目标，且清楚区分“本期做”、“本期不做”与依赖外部实现的部分。

当方案包含多个角色、模块、阶段、主链路或方向选择时，优先用一张 Mermaid `flowchart` 概括“目标或问题 → 核心产品思路 → 主要链路或模块 → 结果与边界”，写入飞书后以画板呈现。画板服务于老板快速判断产品方向，只保留方案骨架和关键关系，不放公式、指标计算、字段、接口、埋点、参数、完整异常枚举或验收用例。相关细节分别放在“二、需求分析”或“四、需求详情”。如果方案简单到一个短段落即可说清，不强制增加画板。

### 四、需求详情

这是首批重点写作章节。对每个实际功能或链路必须写清触发条件、处理规则和可验证的验收标准；异常处理与兜底、上下游依赖只在实际涉及时写入。验收标准应能对应输入、操作或条件与预期结果，不写“效果良好”等无法检查的描述。

`产品`、`推荐`、`数据`、`埋点` 只是候选二级标题，仅在该类内容实际涉及时创建；不得为了套模板而生成空小节。可根据真实链路使用更准确的二级标题。

### 五、数据交付结果至八、需求排期

首稿中，“五、数据交付结果”、“六、指标分析”、“七、问题记录”、“八、需求排期”只生成一级标题，标题下必须完全留空。不得添加表格、示例、占位符、推断、待办说明、“暂无”或任何其他正文。用户后续可以要求起草这些章节的内容，但本 skill 的追加式写入流程不得在已有标题下插入或替换内容。用户可手动粘贴；如需由 Agent 写入原章节，必须确认一个明确独立、不属于本 skill 追加式写入流程的定向编辑任务。不得默认重复创建标题或另写附录。

## 排版与飞书表达

- PRD 的主章节使用一级标题。二级、三级标题只用于内容足以独立展开、需要导航定位的完整分节，层级不得跳级。
- 像“本期范围”“方案边界”这类下方只有几行短内容、无需独立导航的局部标签，使用 `**本期范围：**`、`**方案边界：**` 等**加粗文字**承载，不得使用二级或三级标题；只有内容确实需要分节展开时才升级为标题。
- 默认使用连贯叙事段落；只有真实的行列数据或需要对齐比较的字段才使用表格。
- 数学公式必须使用有效 LaTeX；写入飞书时用 `<latex>...</latex>` 包裹，不得把无效伪代码当作公式。
- 如使用方案概览图或流程图，必须使用 Mermaid `flowchart`：概览图突出主要模块与关系；流程图的动作使用操作节点，条件判断使用菱形决策节点，每条分支边标注条件或结果。写入飞书时用 `<whiteboard type="mermaid">...</whiteboard>` 包裹完整图定义。
- 克制使用高亮块、颜色和分栏；只在能明确强化风险、决策或并列关系时使用，不做装饰性排版。

## 起草与交付检查

1. 确认变更记录的时间、版本号、变更人是否齐全；如有缺失，每次只询问一项。主要变更内容只概括已确认范围；未提供变更原因时，该单元格留空。
2. 仅当用户尚未表明时，询问是否需要“二、需求分析”；用户已明确时不重复询问。如需要，先读现有上下文，仅在分析类型或证据来源仍不清楚时询问。
3. 锁定背景事实、产品方案边界、需求详情与验收条件。
4. 当产品方案具有多个模块、阶段或主链路时，确认“三、产品方案”优先用一张面向老板的高层画板概括方向，且画板中没有公式、字段、接口、埋点、参数或验收细节。
5. 首稿结束前，确认第五至第八章只有一级标题且标题下完全留空。
6. 确认没有生成“产品验收”章节，也没有把本规则文件的说明性标题复制进 PRD。
7. 确认 PRD 正文精确包含 9 个一级标题：聊天预览使用 Markdown `# 标题`，飞书 XML 使用 `<h1>标题</h1>`；不输出 `<title>`，不修改目标文档标题。
